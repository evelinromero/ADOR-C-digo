1. Caso de estudio

1.1 Contexto

Muchas canciones populares nacieron como respuesta a sucesos trágicos: guerras, atentados, represión o injusticias sociales. Con frecuencia su mensaje se expresa con metáforas o en doble sentido, por lo que quien las escucha no siempre conoce la historia que hay detrás. Un ejemplo es “Burka azul”, que hace referencia a la situación de Afganistán mediante dobles sentidos, o “Zombie” de The Cranberries, escrita tras el atentado de Warrington de 1993.

1.2 Problema

La información sobre el contexto histórico de estas canciones está dispersa en artículos, entrevistas y videos. No existe un espacio que reúna en un mismo lugar la canción, su letra, el suceso que representa, la interpretación de lo que dice “entre líneas” y el lugar donde se originó.

1.3 Solución propuesta

Canciones con Historia es una aplicación móvil para Android, desarrollada con Flutter y Firebase, que funciona como catálogo curado de canciones con contexto histórico. El acceso se realiza con la cuenta de Google y existen dos roles:

RolFuncionalidades
UsuarioIniciar sesión con Google · consultar y buscar canciones (por título, banda o suceso) · escuchar la canción (reproductor integrado o enlace a YouTube/Spotify) · leer la letra, el contexto del suceso y el significado oculto · agregar y quitar canciones de favoritos · ver en un mapa el lugar donde se creó la canción.
AdministradorTodo lo anterior, más: agregar canciones mediante un formulario (nombre, banda, año, género, imagen, suceso, contexto, doble sentido, letra, enlaces de audio y ubicación en el mapa) · editar canciones · eliminar canciones.

1.4 Alcance y restricciones

  • Plataforma objetivo: Android (el código Flutter permite compilar también para iOS y Web en el futuro).
  • Proyecto individual con presupuesto cero: se usan únicamente servicios gratuitos (plan Spark de Firebase, mapas de OpenStreetMap).
  • Los administradores se identifican por una lista de correos autorizados, validada tanto en la app como en las reglas de seguridad del servidor.
  • Por derechos de autor, la app no aloja archivos de audio comerciales: reproduce enlaces directos o redirige a plataformas oficiales.

2. Plan del proceso de desarrollo móvil (Kanban)

2.1 Justificación de la metodología

Se seleccionó Kanban porque el proyecto es individual: no hay un equipo que requiera ceremonias de Scrum (Sprint Planning, Daily, roles de Scrum Master y Product Owner). Kanban permite un flujo continuo de trabajo, visualizar el avance de cada funcionalidad, limitar el trabajo en curso para terminar tareas antes de empezar otras y adaptarse a cambios de prioridad (por ejemplo, la configuración de Firebase surgió como tarea bloqueante a mitad del desarrollo).

2.2 Principios aplicados

  1. Visualizar el flujo: tablero con columnas que representan cada etapa del trabajo.
  2. Limitar el trabajo en curso (WIP): máximo 2 tarjetas en “En desarrollo” y 2 en “Pruebas”.
  3. Gestionar el flujo: medir cuánto tarda cada tarjeta en terminarse y detectar cuellos de botella.
  4. Políticas explícitas: cada columna tiene una “definición de terminado”.
  5. Mejora continua: revisión semanal del tablero para ajustar prioridades.

2.6 Métricas de seguimiento

  • Lead time: tiempo desde que la tarjeta entra a “Por hacer” hasta “Terminado”.
  • Cycle time: tiempo que la tarjeta permanece en “En desarrollo” y “Pruebas”.
  • Throughput: número de tarjetas terminadas por semana.
  • Tarjetas bloqueadas: se marcan en rojo con la causa (ej. “falta habilitar Google en Firebase”).

Herramienta propuesta para el tablero: GitHub Projects (vista de tablero), ya que se integra con el repositorio y permite vincular cada tarjeta con su rama y sus commits. Alternativa: Trello.

3. Justificación de la arquitectura

3.1 Arquitectura seleccionada

Se adoptó una arquitectura cliente – Backend as a Service (BaaS), y dentro de la app una arquitectura en capas inspirada en MVVM:

CapaUbicación en el códigoResponsabilidad
Presentación (Vista)lib/screens/, lib/widgets/Pantallas y componentes visuales. No acceden directamente a Firebase.
Estado (ViewModel)lib/state/app_state.dartMantiene el usuario actual, la lista de canciones y los favoritos; notifica a la vista cuando cambian.
Datos (Repositorio)lib/services/backend.dartInterfaz Backend con dos implementaciones: FirebaseBackend y LocalBackend (modo demo).
Modelolib/models/song.dartEntidades Song y AppUser, y su conversión a/desde mapas.
Servicios externosNubeFirebase Authentication, Cloud Firestore, teselas de OpenStreetMap, servidores de audio y YouTube/Spotify.

3.2 Razones de la elección

  • Sin servidor propio: Firebase resuelve autenticación, base de datos y seguridad. Para un proyecto individual elimina el costo de programar, hospedar y mantener una API.
  • Tiempo real: Firestore envía los cambios al instante. Cuando un administrador agrega una canción, aparece en los teléfonos de todos los usuarios sin recargar.
  • Seguridad del lado del servidor: los permisos no dependen solo de ocultar botones en la app; las reglas de Firestore validan en el servidor que solo los correos autorizados puedan escribir canciones.
  • Separación de responsabilidades: las pantallas no saben si los datos vienen de Firebase o del almacenamiento local. Esto facilita las pruebas y permite cambiar de proveedor modificando una sola capa.
  • Modo demo (tolerancia a fallos de configuración): si Firebase no está configurado, la app arranca con LocalBackend y guarda datos en el teléfono. Esto permitió desarrollar y probar la interfaz antes de tener el proyecto de Firebase.
  • Costo cero: las imágenes se comprimen (máx. 900 px, calidad 70 %) y se guardan en Firestore como Base64, evitando Firebase Storage, que requiere el plan de pago. Los mapas usan OpenStreetMap, que no requiere clave de API.

4. Diagrama de la arquitectura

Figura 2. Arquitectura en capas de la aplicación y su relación con Firebase y los servicios externos.

4.1 Flujo de una operación (agregar canción)

  1. El administrador llena el formulario en SongFormScreen; los validadores verifican los campos obligatorios y el formato de los enlaces.
  2. La pantalla construye un objeto Song y llama a backend.saveSong().
  3. FirebaseBackend convierte el objeto con toMap() y lo envía a la colección songs de Firestore.
  4. Las reglas de seguridad verifican que el correo del usuario autenticado esté en la lista de administradores.
  5. Firestore notifica el cambio por el Stream de canciones; AppState actualiza su lista y llama a notifyListeners().
  6. Todas las pantallas que observan el estado se redibujan con la nueva canción, en todos los dispositivos conectados.

5.1 Ejemplo: Repository + Strategy

abstract class Backend {                       // Repository (contrato)
  Stream<List<Song>> songs();
  Future<void> saveSong(Song song);
  Future<void> setFavorite(String uid, String songId, bool fav);
  ...
}
class FirebaseBackend implements Backend { ... }   // Estrategia 1: nube
class LocalBackend    implements Backend { ... }   // Estrategia 2: modo demo

Future<Backend> _createBackend() async {         // Selección en tiempo de ejecución
  try { await Firebase.initializeApp(); return FirebaseBackend(); }
  catch (_) { final l = LocalBackend(); await l.init(); return l; }
}

6.3 Backend: ¿por qué Firebase?

  • Inicio de sesión con Google integrado: requisito principal del caso de estudio.
  • Plan gratuito (Spark) suficiente para el volumen esperado del proyecto.
  • Reglas de seguridad declarativas que permiten implementar los roles de administrador y usuario sin un servidor propio.
  • Alternativas descartadas: una API propia (Node.js/PHP + MySQL) exigiría hospedaje y mantenimiento; Supabase es viable, pero su integración con el inicio de sesión de Google en Android requiere más configuración.

8. Estrategia de versionamiento

8.1 Control de versiones del código

Se utiliza Git (2.52) con repositorio remoto en GitHub, siguiendo un modelo Git Flow simplificado, adecuado para un desarrollador individual:

Figura 4. Flujo de ramas: las funcionalidades se desarrollan en ramas feature y se integran a develop; las versiones estables se publican en main con una etiqueta.
RamaPropósito
mainCódigo estable y entregable. Cada versión publicada se marca con una etiqueta (v1.0.0).
developIntegración de funcionalidades terminadas (columna “Terminado” del tablero Kanban).
feature/<nombre>Una rama por tarjeta Kanban, por ejemplo feature/K-08-favoritos.
hotfix/<nombre>Correcciones urgentes sobre main, que después se integran también a develop.

Convención de mensajes de commit (Conventional Commits)

feat: agregar formulario de canciones para administrador
fix: corregir permiso al guardar canción en Firestore
docs: documentar configuración de Firebase
test: agregar prueba de serialización de Song
chore: reducir memoria de Gradle a 3 GB

8.2 Versionamiento de la aplicación (SemVer)

La versión se define en pubspec.yaml con el formato MAYOR.MENOR.PARCHE+COMPILACIÓN. Actualmente: version: 1.0.0+1.

ComponenteCuándo se incrementaEjemplo
MAYORCambios incompatibles, por ejemplo una nueva estructura de la base de datos que requiere migración.1.4.2 → 2.0.0
MENORNueva funcionalidad compatible, por ejemplo agregar comentarios o notificaciones.1.0.0 → 1.1.0
PARCHECorrección de errores sin cambiar funcionalidades.1.1.0 → 1.1.1
+COMPILACIÓNSe incrementa en cada APK/AAB generado. En Android corresponde a versionCode y debe ser siempre mayor que el anterior para publicar en Google Play.+1 → +2

Proceso de liberación

  1. Actualizar version en pubspec.yaml y registrar los cambios en CHANGELOG.md.
  2. Ejecutar flutter analyze y flutter test (todo en verde).
  3. Integrar develop en main y crear la etiqueta: git tag v1.0.0.
  4. Generar el instalable: flutter build apk --release (o appbundle para Google Play).

f) Reglas de seguridad (firestore.rules)

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isAdmin() {
      return request.auth != null &&
        request.auth.token.email in [ /* correos de administradores */ ];
    }
    match /songs/{songId} {
      allow read:  if request.auth != null;   // cualquier usuario con sesión
      allow write: if isAdmin();              // solo administradores
    }
    match /users/{uid} {                       // favoritos de cada usuario
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
  }
}

10. Conclusiones

El proyecto Canciones con Historia demuestra que una aplicación móvil completa —con autenticación, roles, base de datos en tiempo real, multimedia y mapas— puede desarrollarse de forma individual y sin costo gracias a la combinación de Flutter y Firebase.

Kanban resultó adecuado para un desarrollador individual: permitió visualizar el avance, atender de inmediato las tareas bloqueantes (configuración de Firebase, reglas de seguridad, memoria de compilación) y mantener un flujo continuo sin la sobrecarga de ceremonias de otras metodologías.

La arquitectura en capas y los patrones Repository, Strategy y Observer dieron como resultado un código desacoplado: la interfaz no depende de Firebase, lo que permitió desarrollar primero en modo demo y facilita tanto las pruebas como futuras extensiones.

Como trabajo futuro se plantea completar las pruebas de widgets e integración, firmar la aplicación con una clave propia para publicarla en Google Play, y agregar funciones como comentarios de usuarios, notificaciones de nuevas canciones y una versión para iOS.
